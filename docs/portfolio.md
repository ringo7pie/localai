# localai — 24 GB の GPU 1 枚で、ローカル AI の群れを運用する

> 個人の GPU サーバー（NVIDIA A30 24 GB）に、LLM・3D 生成・画像ワークフローを載せ、
> **取り合う資源（VRAM と RAM）を設計で捌き**、**モデルの良し悪しを測って**、クラウドの Claude Code / Codex から
> 作業を回せるようにした一式。コードと文書とすべての計測記録をこのリポジトリに置く。

| 一言 | 内容 |
|---|---|
| 作ったもの | GPU 排他の入口ページ・MoE 推論サーバーの運用・3D 生成の導入・Claude Code / Codex 連携・モデル評価ハーネス |
| 規模 | 11 のツール（Python・bash・HTML）、追跡ファイルは約 700、計測の記録は JSON で全件保存 |
| 検証 | GPU を使わない単体試験（ツールごと）、実機の疎通試験、10 の AI の比較評価（コーディング・3D 数学ほか） |
| 見てほしい所 | ①資源の排他の設計 ②評価の方法と、それで見つけた事実 ③導入を再現可能にする作法 ④ライセンスの扱い |

## 1. 解いた問題

1. **1 枚の GPU を、複数の重いサービスが取り合う。** Qwen3.8-27B（Ollama）だけで VRAM 22 GiB。
   MoE 推論（Strata）・3D 生成（Hunyuan3D・Pixal3D）・ComfyUI も重みを載せる。同時には載らない。
2. **RAM が足りないと、デスクトップごと落ちる。** 3D 生成の低 VRAM モードは重みを CPU 側へ置く。
   RAM 32 GB でデスクトップごとハングし、RAM を 64 GB に増やした。
3. **「どのモデルを何に使うか」を、感覚でなく測って決めたい。** 速さと正しさの両方を、同じ問題・同じ採点で。
4. **クラウドの AI に作業を頼みつつ、機械的な反復だけはローカルで回したい。** 費用と秘匿の両方を見て。
5. **他人（と未来の自分）が、同じ環境を再現できること。** 上流の版の固定、非対話の導入、再実行しても壊れないこと。

## 2. 設計の判断（と、その根拠）

| 判断 | 何を比べたか・何が分かったか | 根拠 |
|---|---|---|
| GPU の排他を **入口ページと systemd の 2 層**に置く | 画面からの起動と `systemctl` を直に叩く操作の両方で取り合いを防ぐ。Strata 3 種は `Conflicts=`（`After=` は一方向のみ。両側に書くと順序が輪になる） | [architecture.md](architecture.md)・`tools/portal/portal.py` |
| 重いサービスは `enable` しない | PC の自動起動は入口ページだけ。RAM の枯渇でデスクトップがハングした実例から | `knowledge/10-silver/areas/web-services.md` |
| メモリ上限は「**物理の残りより小さく**」 | `MemoryMax` を物理的な残りより大きくしても歯止めにならず、`systemd-oomd` が GNOME Shell ごと落とす。上限の意味は「そのサービスだけを殺してデスクトップを守る」こと | `knowledge/10-silver/resources/service-memory-limits.md` |
| 起動の完了を「**ポートが開いたか**」で判定 | systemd が `active` でも、モデルの読み込み中はポートが閉じている。冷えた状態の Pixal3D の起動は 250 秒（温まった状態は約 80 秒） | `knowledge/10-silver/resources/gpu-exclusive-switching.md` |
| 操作 API に **独自ヘッダを必須**にする | 認証の無い LAN サービスで、ほかのサイトの JavaScript からの単純な POST を、ブラウザの preflight で防ぐ | `knowledge/10-silver/areas/web-services.md` |
| 上流は**固定コミット**で取り込み、直接は直さず `patches/` で当てる | 再実行しても結果が同じ（戻してから当て直す）。1 枚ずつ「当たっているか」を判定する方式は、パッチどうしの文脈行が重なると破綻した（実例あり） | `knowledge/10-silver/resources/hunyuan3d-upstream.md` |
| 3D の背景除去モデルを**ライセンスで選ぶ** | 上流既定の RMBG-2.0 は CC BY-NC 4.0（非商用）。MIT の BiRefNet に差し替えた | `tools/pixal3d/README.md` |
| 評価の問題・採点器・記録を**一緒に版管理** | 後から同じ条件で再採点・比較できる。解説書の本文は問題の原文と照合し、食い違えば HTML を作らず止まる | `tools/model-eval/` |

## 3. 計測した数値

すべて、このリポジトリの記録から取った値（括弧内が根拠）。測定日と条件は元の記録にある。

### 3.1 Qwen3.8-27B（Ollama・Q4_K_M）のコンテキスト長と VRAM

| コンテキスト長 | 配置 | VRAM |
|---|---|---|
| 32,768（既定） | 100% GPU | 19,987 MiB |
| 65,536 | 100% GPU | 22,201 MiB |
| 81,920 | 9% / 91%（CPU / GPU） | 22,569 MiB |
| 131,072 | 28% / 72% | 22,533 MiB |
| 262,144 | 59% / 41% | 22,497 MiB |

→ **65,536 が上限**。それを超えると KV キャッシュが CPU へ溢れ、VRAM に余裕があるように見えて実際は載せるのをやめている
（判定は `PROCESSOR` 列）。生成速度は 23〜26 tok/s。出典: `knowledge/10-silver/archive/setup-inference.md`。

### 3.2 10 の AI の比較評価（同じ問題・同じ採点）

能力 = 問ごとの点数の平均。時間は中央値。出典: [`summary.json`](../tools/model-eval/results/2026-10-08/summary.json)・
[評価レポート](../Documents/AIモデル評価_2026-10-08.html)。

| モデル | 3D 数学（能力 / 時間） | コーディング 6 問 | 追加の 3 試験 |
|---|---|---|---|
| Sonnet 5.5 xHigh | 100% / 67 s | 100% / 46 s | 100% / 2 s |
| Opus 5.5 xHigh | 100% / 62 s | 100% / 59 s | 100% / 3 s |
| qwen3.8:27b（Ollama） | 88% / 873 s | 83% / 243 s | 100% / 13 s |
| gemma4:31b-it-qat | 100% / 3,660 s | 92% / 699 s | 100% / 45 s |
| gemma4:31b-ctx32k | 100% / 441 s | 79% / 266 s | 100% / 51 s |
| gemma4:e4b | 67% / 115 s | 52% / 48 s | 96% / 6 s |
| qwen3.8-flash-next:IQ4_XS | 100% / 3,720 s | 57% / 536 s | 100% / 52 s |
| Strata 公式 IQ3_XXS | 100% / 839 s | 84% / 464 s | 98% / 8 s |
| Strata Coder IQ1_M | 100% / 728 s | 59% / 406 s | 89% / 7 s |

読み方（事実と意見を分ける）:

- 事実: 総合は `0.7 × 能力 + 0.3 × 速度点`（速度点は時間の対数）。Claude 2 種はコーディングで全問合格し、
  能力では差がつかなかった（天井効果）。**この試験では 2 つの順位の差は速さだけ**で、能力の差は測れていない。
- 事実: 試行の回数は少ない（3D は 1〜3 回、コーディングと追加は各問 1 回）。サンプリングありなので、
  同じモデルでも回によって結果は変わりうる。
- 事実: 10 の AI のうち 1 つ（Strata 汎用版 RVN）は、成績が低いとして比較の対象から外した（記録は残してある）。

### 3.3 Strata のコーディング性能の調査（設定の誤りを疑って潰す）

Strata のコーディングの点が低いのは設定の誤りではないか、を条件を変えて調べた。
出典: [調査レポート](../Documents/Strata_コーディング性能の調査_2026-10-09.html)。

| 条件 | Coder IQ1_M の平均 | 公式 IQ3_XXS の平均 |
|---|---|---|
| 思考最大・思考の上限 24,576（最初の評価。基準） | 62% | 69% |
| 思考最大・**上限なし** | 19% | **0%**（6 回とも答えが出ない） |
| low・上限なし（生成 32,768） | 10% | 41% |

- 事実: 設定の誤りは見つからなかった。思考の強さの指示・サンプリング・投機デコード・KV キャッシュの型は、
  Ollama と同じ条件か、結果に影響しないことを確かめた。
- 事実: 最初の評価で付けていた**思考の上限（24,576）は、点を下げる原因ではなく、点を支えていた**。外すと公式は
  6 回とも答えが出ない。49 本のうち 45 本で、思考が上限に届いて打ち切られていた。
- 意見（レポートの所見）: 低い点の原因は、強く量子化したモデルが難しい問題で思考を自分で終えられないこと。
- 実運用の注意: Open WebUI などは思考の上限を送らないので、サーバーの既定（公式 65,536・Coder なし）で動く。

### 3.4 クラウドの AI からローカル Qwen へ委譲する費用

- 事実: 委譲しても、クラウドの費用は減らなかった。5 回の実測で、委譲 / 単独（または Sonnet サブエージェント）の比は
  0.81〜1.15、0.88、2.85。50% 以下は観測しなかった。費用はほぼ「親のターン数 × 文脈長」で、委譲は親のターンを減らせない。
- 事実: 待ちを細かく刻む（`run` → `wait` を親が繰り返す）と高くなる。常駐ループで 1 本待ちにする。
- 判断: 連携層は残し、役割を夜間バッチ・別モデルによるレビュー・ローカルに閉じた作業・他の PC からの利用に絞った。
  費用の削減を目的にはしない。出典: `knowledge/10-silver/areas/local-ai-tools.md`・
  [評価レポート](../knowledge/30-gold/Claude%20サブエージェントとしての%20Qwen%20評価レポート.html)。

### 3.5 3D 生成で見つけた事実

- Pixal3D の多視点経路は、画像の切り抜きも縮小もしない。生成空間は ±0.5 の立方体で、既定カメラでは画面の外周約 9% が
  空間の外になる。余白 0.6% の写真をそのまま渡すと、GLB の上端が境界（0.501）に張り付き、幅 / 高さが 0.65 になった。
  **全視点で縮尺を揃えてから渡す**と、上端 0.459・幅 / 高さ 0.43（入力写真の比 0.41 と一致）に戻った。
  出典: `knowledge/10-silver/resources/pixal3d-upstream.md`。

## 5. 学んだこと・次にやること

- 資源の取り合いは、「誰が止める責任を持つか」を 1 か所に決めると扱いやすい。画面と OS の両方から操作される
  サービスでは、層ごとに同じ規則を持たせる必要がある。
- 数字を出す前に、**条件のそろい方**（思考の上限・生成の上限・言語・サンプリング）を疑う。今回の調査では、
  疑った設定のほうが点を支えていた。
- 次にやること: 評価の試行回数を増やす（今は多くが 1 回）。A30 以外の GPU での導入確認。
  入口ページの認証（今は LAN の信頼が前提）。
