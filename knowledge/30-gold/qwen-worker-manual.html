qwen-worker

ローカルの Qwen3.8-27B を、Claude Code と Codex の両方から呼べる コード調査・実装ワーカーにする。親（クラウド AI）が設計とレビューを持ち、 Qwen が調査・実装・テストコード作成を担当する。

構築日 2026-09-19 / NVIDIA A30 24GiB / Ollama 0.34.2 / qwen3.8:27b (Q4_K_M) / this-host

先に断っておくこと 推論はローカルの Ollama で動く。しかし Qwen が返した要約と差分は親エージェント経由でクラウドへ送られる。 「すべてのコードがローカルだけに留まる」という説明は成り立たない。

01何ができるか

MCP（stdio）サーバー qwen-worker が 3 つのツールを公開する。 いずれも今回作った独自ツールで、既存のものではない。

ツールできること書き込み
qwen_researchコード・資料・ログを調査し、根拠となるファイルと行番号を付けて返す読み取り専用
qwen_implement実装とテストコード作成。隔離された作業コピーで編集し、差分を返す作業コピー内のみ
qwen_status接続先・モデル・有効プロファイル・検証状況・ロック保持者を返す推論しない

単に Ollama へ 1 回質問して答えを返すだけのものではない。 Qwen 自身が検索・読み取り・編集を要求し、その結果を見て次の手を決める ツール呼び出しループが入っている（上限 12 ラウンド）。

05文脈長の実測

各 num_ctx で 1 回 ping を投げ、ollama ps の PROCESSOR 列を読んだ。

VRAM 使用量で限界を判定してはいけない 上の 4 条件の VRAM 使用量は 22053 / 22211 / 22533 / 22553 MiB と、どれも 22 GiB 前後で頭打ちになる。 CPU に溢れても VRAM の数字は増えない。ollama ps の PROCESSOR 列だけが限界を教えてくれる。

large プロファイルは実測に不合格のため無効のまま。指定すると理由付きで blocked が返る。 256K への拡大も q4_0 への変更も行っていない。文脈が足りないときはタスク分割で対応する。

長い入力での測定

入力実測 prompt_eval_count配置VRAM生成
実ソース 72990 文字20328 トークン100% GPU22209 MiB33.0 tok/s

これが「実際に試した入力トークン数」。短い質問が通ったことを 128K 検証済みとは扱っていない。

06入力が黙って消える罠

Ollama はプロンプトを num_ctx / 2 で打ち切り、入力の先頭を黙って捨てる エラーも警告も出ない。done_reason は stop のまま。

再現性のある実測：

num_ctx実測 prompt_eval_countnum_ctx / 2比率
3276816386163840.500
6553632770327680.500

巨大な入力の先頭と末尾にマーカーを置いて確かめた。

先頭マーカー MARKER_ALPHA_7391 が応答に現れた : False
末尾マーカー MARKER_OMEGA_2648 が応答に現れた : True

サーバログで原因を切り分けた。num_parallel による分割ではない。

srv load_model: initializing, n_slots = 1, n_ctx_slot = 65536, kv_unified = 'false'
slot operator(): id 0 | task 49 | new prompt, n_ctx_slot = 65536, n_keep = 4, task.n_tokens = 32770
cmn common_init_: KV cache shifting is not supported for this context, disabling KV cache shifting
ワーカーの対処 推定トークン数が入力予算（既定 24000）を超えたら blocked を返して止まる。 ツール結果が積もった場合に備え、毎ラウンドの開始時にも同じ検査をする。 黙って切り捨てることはしない。超えたら渡す範囲を絞るか、親でタスクを分割する。
トークン数は推定である Ollama 0.34.2 に /api/tokenize は無い（404 を実測）。qwen35 のトークナイザーも手元に無い。 そのため推定値を使い、必ず「推定」と明記している。校正値は実ソース 72990 文字で 推定 26743 / 実測 20328 = 1.32 倍（多めに出る側）。実測は応答の prompt_eval_count を使う。

07安全の境界

守るものやり方検証
許可ルートproject_root は allowed_roots 配下に限る。モデルの申告だけを根拠にしない合格
パストラバーサル判定は realpath（シンボリックリンク解決後）で行う合格
リンク経由の脱出同上。範囲外を指すリンクは拒否合格
秘密ファイル.env / 鍵 / 認証設定は読み込み・複製の対象外合格
元ツリーの保護元の作業ツリーには一切書かない。sha256 を前後比較して確認合格
未コミット変更破棄・stash・reset しない。作業コピーには現在のディスク内容を反映合格
競合検出取り込んだ各ファイルの sha256 を記録し、適用前に変化を検出合格
シェル実行Qwen に任意シェル実行権限を渡さない。未提供のツール名は拒否合格
同時実行flock でプロセスをまたいで 1 件。取れなければ busy合格
git worktree を使っていない worktree は元リポジトリの .git 配下にメタデータを書く。 代わりに baseline/（原本スナップショット）と work/（作業コピー）の 2 つを作り、 git diff --no-index で差分を取る。元リポジトリへの書き込みがゼロになり、git 管理外のプロジェクトでも動く。 差分のパスは a/ b/ に直してあるので git apply -p1 がそのまま通る。

実際に通した受け入れテスト

項目結果
Qwen 自身のツール呼び出しで検索・読み取り合格（3 ラウンドで根拠 5 件）
報告された行番号が実ファイルと一致合格（stats.py:6,13,14,20 / report.py:8 全一致）
作業コピー内でのバグ修正とテスト追加合格（2 タスクとも差分生成）
元の作業ツリーが変更されない合格（sha256 全一致。未コミットの README.md も保持）
差分がそのまま適用できる合格（git apply --check -p1）
作業コピーでテストが通る合格（pytest 3 passed。既存 1 + 新規 2）
範囲外・秘密ファイルへのアクセス拒否合格（境界テスト 17 件 + 実地 6 種）
別プロセスからの同時依頼が直列化合格（B は A の解放を 19 秒待ってから実行）
予算超過を blocked で拒否合格（推定 76279 トークンを拒否）

Codex から

ツール名は同じ。~/.codex/config.toml に登録済み。

クライアントを介さず単体で

cd ~/.local/share/qwen-worker
./.venv/bin/python mcp_call.py qwen_status '{}' 60
./.venv/bin/python mcp_call.py qwen_research '@/tmp/args.json' 1800  # 大きい引数はファイルで渡す

返ってくるもの

親の文脈を圧迫しないよう、長い思考出力と全ログは別ファイルに落としてパスだけ返す。

フィールド内容
statuscompleted / needs_review / failed / blocked / busy
summary短い要約
evidence根拠のファイル・行番号（調査時）
changed_files / diff_path変更ファイル一覧と差分の保存先（実装時）
apply_conflicts取り込み後に元ファイルが変わっていたら中身が入る
verification_not_done未実施の検証。テスト実行と差分適用は常にここに入る
unresolved / next_decision_needed未解決事項と、次に必要な判断
transcript_path / metrics_path全対話と計測値。必要なときだけ読む
completed を鵜呑みにしない 生成上限に達した、差分が空だった、根拠が 1 件も付かなかった場合は needs_review に格下げされ、理由が unresolved に入る。 それでも最終判断は親がすること。Qwen が書いたテストだけでなく、既存テストと完了条件も確認する。

サーバーは stdio。常駐しない。親が必要なときに起動し、セッション終了で落ちる。

# 境界テストを回す
~/.local/share/qwen-worker/.venv/bin/python ~/.local/share/qwen-worker/tests/test_sandbox.py

# ロックが誰かに握られていないか
flock -n ~/.local/state/qwen-worker/inference.lock true && echo 空き || echo 推論中
設定ファイルの落とし穴 TOML ではテーブル見出し（[xxx]）より後ろに書いた key = value は そのテーブルの中に入る。allowed_roots のようなトップレベルの値は必ずファイルの先頭側に置くこと。 （構築中に実際にこれで allowed_roots が [limits] の中に吸い込まれた。）

12他の PC から使う

他の PC の Claude Code / Codex は、SSH でこのホストに繋いで stdio のまま MCP をやり取りする。 他 PC 側に Python も Ollama も要らない。コードもこのホスト側にあるものを触る。

鍵の受け入れと取り消し（このホスト側）

# 受け入れ
bash ~/.local/share/qwen-worker/remote/add-remote-key.sh <PC名> <公開鍵ファイル>

# 一覧と取り消し
bash ~/.local/share/qwen-worker/remote/remove-remote-key.sh --list
bash ~/.local/share/qwen-worker/remote/remove-remote-key.sh <PC名>

authorized_keys に書かれる行はこの形になる。

command="/home/mt/.local/share/qwen-worker/run-qwen-worker",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding ssh-ed25519 AAAA... qwen-worker@<PC名>
実測で確かめたこと この鍵で ssh ... 'id' を投げても id は実行されず、MCP の initialize 応答が返った。 SSH 越しに qwen_status と qwen_implement を実呼び出しし、差分生成まで通した（34.7 秒、30 行の差分）。

意図的に切ってある設定

次の 4 つを false にしてある。いずれも同じモデルで裏側の追加推論を走らせる機能で、 Ollama が生成を 1 本ずつ処理する以上、1 発言ごとに順番待ちが増えるため。

変数効果
ENABLE_TITLE_GENERATION会話タイトルの自動生成
ENABLE_TAGS_GENERATIONタグの自動生成
ENABLE_FOLLOW_UP_GENERATION追質問の候補生成
ENABLE_AUTOCOMPLETE_GENERATION入力補完

変数名はインストール済みの open_webui/env.py / config.py に実在することを確認済み。 一般に紹介される SCARF_NO_ANALYTICS と ANONYMIZED_TELEMETRY は この版のコードに存在しなかったので書いていない。

最初の 1 人を登録したら登録を閉じる ENABLE_SIGNUP=true のまま起動している。最初に登録した人が管理者になる。 登録したら次を実行すること。
sed -i 's/^ENABLE_SIGNUP=true/ENABLE_SIGNUP=false/' ~/.config/open-webui/open-webui.env
systemctl --user restart open-webui

GPU の共有

ワーカーとブラウザチャットは同じ GPU・同じモデルを使う。Ollama は生成を 1 本ずつ直列に処理する。

ワーカー実行中でもブラウザは応答することが多い ワーカーはモデル生成とローカルのファイル操作を交互に行うため、ファイルを読んでいる間は Ollama が空く。 実測では、ワーカーのジョブ（16.2 秒）が走っている最中にブラウザ相当の短い質問を送ったところ 2 秒で返った。待たされるのは「相手の 1 回の生成が終わるまで」であって、ジョブ全体ではない。
Open WebUI 側で num_ctx を上げないこと 既定は Ollama 側の OLLAMA_CONTEXT_LENGTH=65536。 これを超えると KV キャッシュが CPU に溢れる（→ 05）。
